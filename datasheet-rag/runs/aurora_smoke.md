# Cycle 2 step 1: Aurora smoke test (2026-10-16)

> Update, step 2 (2026-10-17): the direct connection was chosen. The `data-api` command and `resume --path` were removed from the script. It now has `direct` and `resume`, both through `db.connect()` with `DB_TARGET=aurora`.

Result: **passed.** Aurora PostgreSQL Serverless works for this project on the Free plan. pgvector, pausing at 0 ACU, and access from outside a VPC all work. Both ways of reaching the database (a direct connection and the Data API) worked. The recommendation for step 2 is the direct connection.

## Setup

- **Created by the human in the console**: express configuration, the only kind the Free plan allows.
  - Cluster `datasheet-rag`, us-east-1, one serverless instance.
  - Capacity: minimum 0 ACU, maximum 4 ACU (the Free plan limit), pause after 5 minutes idle.
- **Engine: Aurora PostgreSQL 17.9** on ARM (aarch64), with **pgvector 0.8.1**.
  - Express configuration always uses AWS's default version, which can be upgraded but never downgraded.
  - Locally we run PostgreSQL 16 (`pgvector/pgvector:pg16`). All of `rag/db.py` ran unchanged on 17.9.
- **No VPC.** The cluster is reached over the internet through the "internet access gateway" on port 5432.
  - Login is IAM authentication only: a 15-minute token takes the place of a password.
  - The master user is `postgres`. Its token is generated by CloudShell.
- **Database roles**, created by the human in CloudShell:
  - `rag_app` has `rds_iam` and logs in with an IAM token. This is the direct way.
  - `rag_data` has a password, kept in the Secrets Manager secret `datasheet-rag/rag_data`. This is for the Data API, which cannot use the master user on an express cluster.
  - Both roles have CREATE on the database and on schema `public`.
- **The Data API** was turned on with `aws rds enable-http-endpoint`, run in CloudShell. The console's Modify page has no setting for it on an express cluster.
- **The dev IAM user** got an inline policy, `rag-aurora-smoke`, with three permissions:
  - `rds-db:connect` for `rag_app`;
  - `rds-data:ExecuteStatement` on the cluster;
  - `secretsmanager:GetSecretValue` on the secret.

Two notes on the connection:

- The certificate is checked with `sslmode=verify-full`. With only `require`, the connection is encrypted but the server is not checked, so a fake server could collect the 15-minute token. The gateway's certificate chains to Amazon's public root CAs.
  - On Windows, libpq's `sslrootcert=system` points at OpenSSL's store, which is empty there, so it fails with "certificate verify failed".
  - The script uses the CA bundle that ships with botocore instead. In Lambda (Linux), check which bundle to use in step 2.
- Data API times are measured with one client per run. Building a boto3 client for each call had added about 0.2–0.3 s to every call.

## Recommendation for step 2

Use the **direct connection** (psycopg with an IAM token) and not a Data API backend:

- Every function in `rag/db.py` already ran on Aurora unchanged. Step 2 only needs `db.connect` to take an IAM token and `sslmode=require`; there is no second backend to write or test.
- The Data API's main advantage was keeping Lambda out of a VPC. An express cluster is already outside any VPC, so Lambda can connect directly.
- Resume times are the same for both ways (about 18 s).
  - Lambda's timeout must allow for a resume.
  - The first request after a pause needs a retry, or a connect timeout well above 15 s; 60 s is used here.
- What Lambda will need:
  - `rds-db:connect` in its role;
  - the Linux `psycopg[binary]` wheel in its package (the `python3.14` runtime exists, on AL2023 and arm64 or x86_64);
  - one connection kept between warm invocations.

If step 2 confirms this choice, the human removes the Data API parts:

- the secret `datasheet-rag/rag_data`, which costs $0.40 a month while it exists;
- the `rag_data` role;
- the Data API endpoint (`aws rds disable-http-endpoint`);
- the two Data API statements from the `rag-aurora-smoke` policy.
